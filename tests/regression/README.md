# tests/regression/README.md

가짜정보탐지 정확도/속도 회귀 테스트셋. pytest가 아니라 **데스크탑에서 수동으로** 돌린다 -
실제 위키 인덱스(build_wiki_index.py로 미리 구축), 반박 확인용 NLI 모델(train_nli.py로 미리 학습,
기본 위치 `data\nli_model_aug` - 서버와 같은 기본값이다, 다른 곳이면 `--nli-model`로 지정), Ollama가 모두
준비돼 있어야 한다.

## 언제 돌리나

- 프롬프트(`scripts/misinfo_lib.py`의 `EXTRACT_TEMPLATE`, `JUDGE_TEMPLATE`)를 바꿀 때
- `MISINFO_EVIDENCE_CHUNK_COUNT`, Ollama 모델 이름 등 설정값을 바꿀 때
- 위키 인덱스를 재구축한 뒤

## 실행

```powershell
conda activate text-extraction
cd C:\ai\veritae-detection-server\tests\regression
python run_regression.py --wiki-index C:\ai\veritae-detection-server\data\wiki_index.sqlite3 --ollama-url http://localhost:11434 --ollama-model qwen3.5:4b
```

## 데이터셋

- **`cases_e2e.json`(20건, 기본 실행 대상 = 머지 게이트)**: 실제 위키 검색으로 후보를 찾고 e5로
  재정렬해 Ollama에 판정을 맡기는, 실제 파이프라인 그대로 돌리는 세트다. 2026-09-29 실측 16/20,
  2026-09-30 실측 19/20(거짓 11건 중 아폴로 1건만 놓침).
- **`cases_grounding.json`(14건, 기본 실행 대상 = 머지 게이트)**: 2026-10-01 실제 분석에서
  "라벨은 반박인데 근거는 속설을 뒷받침"한 사례를 계기로 추가했다. 전해 들은 말("~라고
  들었어요", 안의 내용으로 판정), OCR 오타, 속설 소개("~라는 속설이 있다" - 2026-10-14부터 속설
  내용으로 판정), 속설을 부정하는 맞는 말("~는 잘못 알려진 것이다" - 반박되면 안 됨), 근거 두 개를
  이어 봐야 하는 문장을 담는다.
- **`cases_heldout.json`(25건, 기본 실행 대상 = 머지 게이트)**: 2026-10-01 근거 문장 선택 단계를
  넣으면서, 결과를 보기 전에 새로 만든 확인용 세트다. 프롬프트를 고칠 때 이 세트의 결과에 맞춰
  고치지 않는다 - 앞의 두 세트에만 맞춘 수정인지 가려내는 용도다. 틀린 사실, 속설, 참인 사실,
  속설 소개, 전해 들은 말, 개인적인 이야기를 섞었다.
- **`cases_realistic.json`(60건, 기본 실행 대상 = 머지 게이트, 2026-10-14 추가)**: 앞의 세 세트는
  평균 17~24자의 교과서 문장이고 주제가 약 20개로 겹쳐서 실제 입력(카톡·뉴스 캡처, 통화)을 대표하지 못했다.
  구어체·카톡 형태의 거짓 주장 16건, OCR 오타(를→틀, 었→없)가 섞인 거짓 주장 3건, 속설 소개("~라고
  주장하는 사람들이 있대", "~라는 음모론이 있다") 2건, 속설을 부정하는 맞는 말("~는 다 미신이래요") 9건,
  구어체로 쓴 참인 사실 12건, 일상 대화 13건, 위키로 확인할 수 없는 소식 6건이다. 거짓 주장은 위키에
  근거가 있다고 기록으로 확인된 주제만 썼다. 결과를 보기 전에 만든 확인용 세트라 **프롬프트를 이 세트
  결과에 맞춰 고치지 않는다.**

**판단 기준(2026-10-14 사용자 결정)**: 문장이 결국 말하는 내용으로 판단한다. 전해 들은 말("~라고
들었어요")과 속설 소개("~라는 속설이 있다", 분류 `mention`)는 그 내용이 거짓이면 거짓으로 탐지돼야 하고,
속설을 부정하는 문장("~는 사실이 아니다", 분류 `negation`)은 맞는 말이라 표시되면 안 된다. 그 전에는 속설
소개 문장을 "속설이 있다는 사실"로 판단해 표시되면 안 되는 것으로 정해 두었는데, 사용자 결정이 아니었고
깨진 OCR 문장을 이 유형으로 착각해 탐지를 놓치는 원인이 됐다.
- **`cases_basic.json`(36건), `cases_hard.json`(16건, 참고용 - 머지 게이트 아님)**: 원래 NLI
  분류기 실험용 데이터로, 문장마다 근거 문단(premise)이 함께 주어져 있었다. 이 브랜치로 옮겨
  오면서 `sentence`만 남고 premise가 빠졌는데, 연예인 사망설/"이 약은…"/"A시에…" 같은 문항은
  근거 문단이 있어야 성립해서 실제 위키 검색으로는 재현이 안 된다 - 즉 36/36·16/16 기준과 지금
  비교할 수 없다(2026-09-30 리뷰에서 확인, 컨트롤러 판단). premise를 살린 NLI 전용 모드를 새로
  만드는 건 범위 밖(YAGNI)으로 보류했다 - 지금은 `--include-nli-legacy` 플래그를 줬을 때만
  참고용으로 같이 돈다.

## 판단 기준

- 각 그룹이 정확도, "위험 오답"(참인데 거짓으로 판정) 건수, 잘못된 근거 문장 건수, 가장 느린
  문장의 시간을 출력한다.
- 반박이어야 하는 문장에는 `evidence_keys`(단어 묶음 목록)가 있다. 화면에 나갈 근거 문장이 모든
  묶음에서 단어를 하나 이상 포함하지 않으면 `[BAD-EVIDENCE]`로 표시한다(2026-10-01: 라벨은 맞는데
  "지구의는 받침대에 베어링이 있다" 같은 무관한 문장이 근거로 나간 사례). 자동 채점이 다른 표현을
  놓쳤을 수도 있으니, 표시된 근거는 **한 건씩 읽어서 확인한다.**
- 통과 조건: 네 세트 모두 위험 오답 0건, 잘못된 근거 문장 0건. 잡아낸 거짓 문장 수는 직전
  실측과 비교해 함께 보고한다.
- 그룹마다 `결과별 문장 수`(outcome별 개수)를 출력한다. 거짓 문장을 놓쳤을 때 검색·판정 중 어디서
  끝났는지 본다(outcome 뜻은 레포 README의 "로그 읽는 법" 표).
- `--dump-candidates`로 저장한 기록에는 문장마다 LLM 판정(`first`: 핵심 주장, 인용 문단, 이유, 판정)과
  `outcome`, 후보 문장 전체의 NLI 점수가 들어 있다.
- `cases_basic.json`/`cases_hard.json`(참고용)의 결과는 지금 파이프라인과 직접 비교할 수
  없으니 정확도 숫자 자체보다는 "터지지 않고 도는지" 정도만 참고한다.

## 판정 방식(2026-10-18)과 이 회귀 도구

서버 기본 판정 방식은 `split`(README '판정 방식')인데, `run_regression.py`는 판정 함수 `judge_sentence`를 직접 불러 **`current` 흐름만** 잰다. `split`과의 비교는 `scripts/measure_final.py`(지금·나눔·나눔+A·제목검색, 기존 225문장 + 새 문장 `cases_fresh2.json`)로 한다. 판정 방식을 바꾸거나 판정 지시문을 고친 뒤에는 그 도구로 다시 재고, 서버 경로는 `scripts/check_image_e2e.py`로 확인한다.
